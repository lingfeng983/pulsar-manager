## 二、批次 6：手动 ack / nack + 死信 + 游标回放

方案 §2「手动 ack 协议」、§3 `consumer:ack/nack/seek`、§5 `AckToolbar` 是这一批的全部内容。`shared/types.ts` 里 `Message.ackSeq`（`:269`）和 `messageIdBytes`（`:272`、seek 载荷 `:584`）**已经声明但全仓库无人赋值**（`grep -rn ackSeq src/` 只命中 types），这一批就是把管线接上。

主进程：

1. `PendingAcks`（新文件或与 `pulsar-native-client.ts` 同放，跟着 session 走）：以**单调 `seq`** 为键持有原生 `Message` 对象。不用 `messageId.toString()` 当键——批消息里多条的 `(l=,e=,p=)` 可能相同，会串消息。双阈值 `MAX_PENDING_ACKS = 1000` 与 `MAX_PENDING_BYTES = 64MB`，被淘汰的条目标记「超出可确认窗口，将由 broker 重投」并计入界面提示；这条不写就是主进程内存增长 bug。
2. `autoAck === false` 时 `buildConsumerConfig` 必须带上 `batchIndexAckEnabled: true`，否则逐条 ack 不推进 `markDeletePosition`，界面显示已确认而积压不降。
3. `toRendererMessage` 增第二个入参：写入 `ackSeq`（同会话自增）与 `messageIdBytes = message.getMessageId().serialize()` 的 base64；顺带把序列化字节数喂给 `PendingAcks` 的字节阈值。
4. `pump` 的 flush 判定补第三条件：累计 base64 字节 ≥ 4MB 立即 flush（现在只有 50 条 / 300ms，50×5MB 会一次过界）。
5. `ack` / `nack` / `seek` 三个方法进 manager：ack 前校验 `!session.stopped`（consumer 关闭后再 nack 是 use-after-free，实测会段错误）；`nack` 走同步 `negativeAcknowledge`；`seek` 用 `MessageId.deserialize(Buffer.from(bytes,'base64'))`，只有活着的 consumer 能做，否则退到 admin `resetcursor/{timestamp}`（带时间戳可用，无参 500）。
6. `consumer-handlers.ts` 加 `consumer:ack` / `consumer:nack` / `consumer:seek`，都用 `registerHandler`（句柄在 manager 单例里，不建连），文件顶部注释写明这点，否则像漏写 registrar。schema 进 `_shared.ts`：`ConsumerAckSchema`（cumulative 只认一条，`.refine` 钉住）、`ConsumerSeekSchema`（`messageIdBytes` 与 `timestamp` 二选一）。

渲染层：

7. `MessageListView` 加 `rowSelection`，仅在 `autoAck === false` 的会话显示；列里补 seq 与「未确认」状态。
8. `AckToolbar`（`components/consumer/AckToolbar.tsx`，新建）：确认所选 / 累计确认到所选 / nack 所选 / 全确认 / 全 nack，指标行补「未确认 N」。
9. `useMessageStream` 要在会话结束或超出窗口时把对应的 pending 条目清掉，避免 UI 上还能点已失效的 seq。
10. preload 三处同步：通道字面量、API 方法、`declare global` 类型（漏第三处就是渲染层 `any`）。

可绿条件：三项绿 + CDP 实机，**且必须真在 broker 上验证逐条 ack 后积压下降**：
- 关自动确认起会话，`messages.send` 20 条，读 `refreshBacklog` 的 `messageCount` = 20；逐条确认全部，再刷新积压 = 0（这一步不做等于整个批次没验证）。
- nack 一条后按 `nAckRedeliverTimeoutMs` 能看到它重投回来（seq 变了、内容一致）。
- 把 `maxMessages`/上限压低或连发 >1000 条，确认「超出可确认窗口」提示出现且主进程 RSS 不持续涨。
- 同一 topic 并开两个 Shared 会话不互踢；`seek` 回放到某条消息后重新收到它。
- 三主题截图：AckToolbar、复选框、「未确认」标记在 dark/eyeCare 下可读。

## 三、批次 7：peek 最近消息、重发、发送历史、消息定位

1. `messages:peekLatest`（留 `message-handlers.ts`，走 `trackShortLived`）：一次性非会话 Reader，`createReader({startMessageId: earliest}) → seekTimestamp(now - windowMs) → 轮询收满 count / scanLimit / deadline`。**注释必须写明陷阱**：`hasNext()` 同步且只看本地队列，新建 Reader 队列必空，首个 `!hasNext` 绝不能当结束条件，要「连续 N 次空轮询或墙钟到期」；`readNext()` 不带参数，整体套 `withHardTimeout`。
2. `messages:resend`（native）：取该条 `data` + properties 再 `send` 一次，与 seek 回放分开（重发产生新消息，回放是移动游标）。`MessageResendSchema` base64 上限 7MB ≈ 5MB 膨胀。
3. `send_history` 读写：`insertSendHistory` 在 `messages:send`、`producer:sendOnce`、连续发送结束、`messages:resend` 四处都写，`.catch(()=>undefined)`——记历史失败绝不能把发送报成失败；只存正文前缀（`body_preview`）与字节数，不存解析后载荷。`cleanupSendHistory(maxRows = 2000)` 在 `initDatabase` 里紧挨 `cleanupOperationLogs()` 调用，**不自动 VACUUM**，注释写原因。
4. `sendHistory:list` 通道 + ProducerWorkspace 的历史抽屉（模板名 / 时间 / 条数 / messageId / 状态 / 错误，失败可重发）。
5. 「消息定位」时间线：Reader 按时间窗扫描 + 按 property 或前缀过滤，叠加 topic `/stats` 的 producers / subscriptions / backlog 快照。**UI 文案就叫「消息定位」，不要写「消息追踪」**（broker 侧 `PulsarMessageTracer` 默认关闭、admin 无 trace 路由，做不了真 trace）。
6. `getMessagesById` 只做在本会话收到过的消息上（靠已缓存的 `messageIdBytes` seek），admin 路由 404。

可绿条件：三项绿 + CDP 实机（peek 10 条能出、resend 后消费者收到新那条、历史列表有上述四处的记录、清理 2000 条上限生效、三主题截图）。

- 生产实例占单例锁，`--user-data-dir` 必须换成本仓库外的新目录。

- better-sqlite3 要编到 Electron ABI（`NODE_MODULE_VERSION 121`），换 Electron 版本后先重建。

- 已知坑：`Runtime.enable` 会重放本次会话里的旧页面异常，别重复诊断已修好的；`[aria-label=…]` 在 AutoComplete/Select 上同时命中外层 DIV 和内层 INPUT，写值要先 `box.querySelector('input')`；`:text(文本|选择器)` 的选择器要页面作用域（如 `:text(停止|.consumer-side button)`）；antd `loading` 按钮吞点击；含正则的探针写成 `.mjs` 文件而不是 `node -e`；改 JS/TS 文件一律用 Edit 工具，别用 perl 一行流（`${JSON.stringify(...)}` 会被 perl 吃掉）；探针不要用 `finally { process.exit(0) }` 吞错。
- 原生绑定红线：`batchingEnabled: true` 与 `chunkingEnabled: true` 同时开会让整个主进程 abort（四层守卫已在位，别绕过）；`Reader.readNext(timeout)` 超时到期时段错误。
