# 插件编写说明

本文对应插件系统 `src/main/services/plugin-service.ts` 的实现，面向想给 pulsar-manager 增加压测预设或 Topic 模板的开发者与运维。

## 0. 一句话说清边界

插件是**一份 JSON 数据**。应用只读取它贡献的参数，不加载、不执行插件里的任何代码，也不让插件访问网络、文件系统或数据库。因此：

- 写插件不需要写 JavaScript，也不需要打包；
- 一个坏插件最多让某条预设不出现（或让插件市场显示一条加载失败），不会把主进程带崩；
- 反过来，插件能做的事情也仅限「填表单」：压测参数预设、新建 Topic 时的模板。

当前支持的贡献类型只有两种：`benchmarkPresets`（快速压测预设）与 `topicTemplates`（Topic 创建模板）。

## 1. 最小可用插件

把下面内容保存为 `acme-bench.json`：

```json
{
    "id": "acme-bench",
    "name": "Acme 压测预设",
    "version": "1.0.0",
    "description": "给 128 分区 topic 用的两档预设",
    "author": "Acme SRE",
    "contributions": {
        "benchmarkPresets": [
            {
                "name": "稳态 20k",
                "description": "4 生产者、限速 20000 msg/s、开批",
                "params": {
                    "producers": 4,
                    "totalMessages": 200000,
                    "messageSizeBytes": 512,
                    "ratePerSecond": 20000,
                    "maxInFlightPerProducer": 200,
                    "batchingEnabled": true,
                    "compression": "LZ4",
                    "consumeBacklog": false
                }
            }
        ]
    }
}
```

在「设置 → 插件市场 → 导入插件文件」选中它，随后打开「快速压测」，预设下拉里会出现「Acme 压测预设 · 稳态 20k」。选中只覆盖压测参数，不覆盖集群、租户、命名空间、topic 与订阅——这些必须由使用者自己选。

只要模板的插件：

```json
{
    "id": "acme-topics",
    "name": "Acme Topic 规范",
    "version": "1.0",
    "description": "按环境约定预填分区数",
    "contributions": {
        "topicTemplates": [
            {
                "name": "业务标准",
                "description": "持久 + 8 分区",
                "persistent": true,
                "partitions": 8,
                "namePrefix": "biz-"
            },
            {
                "name": "临时事件流",
                "description": "非持久、不分区",
                "persistent": false,
                "partitions": 0
            }
        ]
    }
}
```

两种贡献可以写在同一个插件里，但整个 `contributions` 至少要有一条内容，空对象会被拒绝。

## 2. 安装位置与加载规则

插件目录是 Electron 的 `userData/plugins`，界面上的位置在「插件市场」底部，也可以点「打开插件目录」直接打开：

| 平台 | 默认路径 |
|------|----------|
| Windows | `%APPDATA%\pulsar-manager\plugins` |
| macOS | `~/Library/Application Support/pulsar-manager/plugins` |
| Linux | `~/.config/pulsar-manager/plugins` |

加载器只认两种摆放方式：

```
plugins/
├── acme-bench.json          ← 直接放 JSON 文件
└── acme-topics/
    └── plugin.json          ← 或放一个目录，入口固定叫 plugin.json
```

- 顶层只扫描 `.json` 文件（扩展名大小写不敏感），不递归更深层；
- 目录里没有 `plugin.json` 会作为一条加载失败显示出来，不会被静默忽略；
- 同目录下的其它文件（README、图片等）不会被读取。

三种安装方式最终都落到同一个文件：

1. **导入插件文件**（推荐）：渲染层读成文本发给主进程，主进程只认内容、不碰路径，校验通过后写成 `plugins/<id>.json`。文件大小上限 200,000 字符；**同 id 会直接覆盖旧文件**。
2. **手动放置**：把 JSON 放进插件目录，回到插件市场点「刷新」。手动放置的文件没有导入通道的 200,000 字符上限，建议仍保持小体积。
3. **官方目录安装**：官方插件随应用打包（见 `src/main/services/official-plugins.ts`），未安装时也显示卡片，点「安装」后同样写成 `plugins/<id>.json`。

覆盖规则有一个容易误解的地方：如果本机存在与官方插件**同 id** 的文件，本地文件的内容优先，但卡片来源仍显示「官方」、状态显示已安装——这是为了不让用户点完安装后看到卡片突然变成另一个插件。官方目录当前包含：

| id | 内容 |
|----|------|
| `pm-smoke-benchmarks` | 快速冒烟、吞吐洪峰、延迟探测、大消息 |
| `pm-end-to-end-benchmarks` | 恒定速率读写、积压追赶 |
| `pm-topic-templates` | 标准分区、单分区持久、非持久事件流、高分区 |
| `pm-batch-tuning` | 关批量、开批量、开批量 + Snappy |

不要用两个文件声明同一个 `id`（例如既有 `x.json` 又有 `x/plugin.json`）：它们会被当成同一个插件的两个来源，最终展示哪一个取决于目录遍历顺序，属于未定义行为。

## 3. 清单字段参考

校验用 zod 一次性完成，失败时插件市场顶部会列出**文件名 + 第一条错误**（例如 `acme.json: contributions.benchmarkPresets.0.params.producers: Number must be greater than or equal to 1`）。校验不过的文件不会落盘、也不会部分生效。

### 3.1 顶层字段

| 字段 | 必填 | 规则 |
|------|------|------|
| `id` | 是 | `/^[a-z0-9][a-z0-9._-]{1,63}$/`，2–64 位，首字符必须是字母或数字；只允许小写字母、数字、点、下划线、连字符 |
| `name` | 是 | 1–60 字符，插件市场与预设下拉里显示它 |
| `version` | 是 | `/^\d+\.\d+(\.\d+)?$/`，只接受 `1.0` 或 `1.0.0` 这种形式，不接受预发布后缀 |
| `description` | 否 | ≤200 字符 |
| `author` | 否 | ≤60 字符 |
| `contributions` | 是 | 见下；至少贡献一条预设或一个模板 |

`id` 同时是文件名、启用状态与卸载操作的键，发布后不要再改：改了等于换了一个插件，旧文件仍会留在目录里。

### 3.2 `benchmarkPresets`

```json
{
    "name": "稳态 20k",
    "description": "可选，≤120 字符",
    "params": {
        "producers": 4,
        "totalMessages": 200000,
        "messageSizeBytes": 512,
        "ratePerSecond": 20000,
        "maxInFlightPerProducer": 200,
        "batchingEnabled": true,
        "compression": "LZ4",
        "consumeBacklog": false
    }
}
```

| 参数 | 类型 | 范围 | 含义 |
|------|------|------|------|
| `producers` | 整数 | 1–64 | 并发生产者数 |
| `totalMessages` | 整数 | 1–10,000,000 | 本次总发送条数 |
| `messageSizeBytes` | 整数 | 1–10,485,760 | 每条消息字节数（上限 10 MB） |
| `ratePerSecond` | 整数 | 0–1,000,000 | 总限速；`0` 表示全速不节流 |
| `maxInFlightPerProducer` | 整数 | 1–10,000 | 每个生产者的在途上限，越大吞吐越高、延迟越差 |
| `batchingEnabled` | 布尔 | — | 是否开批 |
| `compression` | 字符串 | `None` / `LZ4` / `Zlib` / `SNAPPY` / `ZSTD` | **大小写敏感** |
| `consumeBacklog` | 布尔 | — | 是否边压边消费（端到端模式） |

每条预设的 `name` 为 1–40 字符、`description` ≤120 字符；每个插件最多 20 条。

注意：

- `messageSizeBytes` 是应用层上限，不代表 broker 允许。broker 的 `maxMessageSize` 更小的时候，压测会在发送阶段收到服务端拒绝；预设里应写目标集群实际能接受的尺寸。
- 预设只提供参数，不指定目标。快速压测弹窗里选中预设后，集群 / 租户 / 命名空间 / topic 仍由使用者填写，这是刻意的：一份预设不应该替人决定往哪里打流量。
- 参数是**真实会发出去的流量**。`totalMessages: 10000000` × `messageSizeBytes: 10485760` 在纸面上合法，实际是 100 TB 级写入。schema 上限不是安全边界，导入别人的插件前先读一遍参数。

### 3.3 `topicTemplates`

```json
{
    "name": "业务标准",
    "description": "可选，≤120 字符",
    "persistent": true,
    "partitions": 8,
    "namePrefix": "biz-"
}
```

| 字段 | 必填 | 规则 | 含义 |
|------|------|------|------|
| `name` | 是 | 1–40 字符 | 模板名 |
| `description` | 否 | ≤120 字符 | 卡片与下拉里的说明 |
| `persistent` | 是 | 布尔 | 持久 / 非持久 |
| `partitions` | 是 | 整数 0–128 | 0 表示不分区 |
| `namePrefix` | 否 | `/^[a-zA-Z0-9._-]{0,40}$/` | 新建 Topic 时，名称框为空才用它填充 |

每个插件最多 20 个模板。套用时的两个固定行为：**非持久模板一律把分区数归 0**（Pulsar 的非持久 topic 不支持分区）；`namePrefix` 只在名称框为空时生效，不会覆盖用户已经输入的名字。

### 3.4 未知字段与类型

- zod 默认是「剥离未知字段」而不是报错：多写的键会被静默丢弃。因此把 `consumeBacklog` 拼成 `consumebacklog` 不会提示「未知字段」，而是报缺少必填项——看到 `Required` 先检查拼写。
- 数字必须是 JSON number，不能写成 `"200000"`；布尔必须是 `true/false`，不能写 `"true"`。
- 文件必须是合法 UTF-8 JSON，不接受注释与尾逗号。

## 4. 启用、刷新与生效时机

- 装好的插件默认启用；关闭启用开关后，文件仍在，贡献的预设/模板从界面消失。停用状态存在本机数据库 `user_settings` 的 `disabledPlugins` 键里（JSON 数组）。
- 卸载会删除 `plugins/<id>.json` 与 `plugins/<id>/` 目录，并清掉停用记录；路径在服务层被钉死在插件目录内，`id` 也先过正则，避免把 `../` 拼进删除路径。
- **没有文件监听**：手动改了 JSON，要回插件市场点「刷新」（或重启应用）才会重新读取。导入、启用/停用、卸载成功后界面会自动重读。
- 渲染层在应用启动时加载一次插件，之后从「已启用条目」派生 `presets` / `templates` 两个列表。停用插件不会影响正在跑的压测，也不会改变已经创建好的 Topic。
- 预设下拉的选项值是 `<pluginId>#<预设名>`。同一个插件内两条预设**不要重名**：下拉会出现两个相同 key，React 会告警，选中也会产生歧义。不同插件之间的同名预设没问题。

## 5. 安全模型

插件系统刻意只做「数据贡献」，因此攻击面只有数据解析与数据使用：

- 不执行插件代码，不 `eval`、不 `require`，没有插件进程或 Worker；
- 不读取插件目录之外的文件；导入只接收文本，主进程不碰渲染层给的文件路径；
- `id` 正则同时约束文件名与卸载目标；卸载前再用 `path.resolve` 判断目标是否在插件目录内；
- 校验失败会展示原因，不静默丢弃；
- 插件数据只进入两个既有表单：快速压测参数、新建 Topic 表单。

但「不执行代码」不等于「没有风险」：

- 预设会真的打出流量（见上文的参数上限），模板会真的创建 topic。只导入可信来源的插件。
- 手动放进目录的 JSON 没有 200,000 字符的导入上限，超大文件会在主进程同步读取/解析时占住事件循环。自己写插件时保持文件在几十 KB 以内。
- 插件内容会原样显示在插件市场（名称、描述、作者），不要往这些字段里塞凭据。

## 6. 排错表

| 现象 / 报错 | 原因 | 处理 |
|-------------|------|------|
| 卡片没出现 | 文件不在 `userData/plugins`、不是 `.json`、或放进了更深层目录 | 用「打开插件目录」确认位置，点「刷新」 |
| `目录里没有 plugin.json` | 放了子目录但入口文件名字不对 | 改名成 `plugin.json`，或把 JSON 直接放顶层 |
| `不是合法的 JSON：...` | 注释、尾逗号、BOM、中文引号 | 用 JSON 校验器过一遍 |
| `id 需为 2~64 位小写字母、数字、点、下划线或连字符` | 大写、空格、以点/连字符开头 | 按正则改名，并同步改文件名 |
| `version 需形如 1.0 或 1.0.0` | 写了 `v1.0`、`1.0.0-beta` | 改成两段或三段数字 |
| `contributions: Required` | 漏了整个 `contributions` | 补上并至少放一条预设/模板 |
| `插件至少要贡献一条压测预设或 Topic 模板` | 两个数组都为空，或键名拼错被剥离 | 检查 `benchmarkPresets` / `topicTemplates` 拼写 |
| `contributions.benchmarkPresets.0.params.xxx: Required` | 参数缺项或键名拼错 | 对照 3.2 的完整字段表 |
| `contributions.benchmarkPresets.0.params.producers: Number must be greater than or equal to 1` | 越界 | 按 3.2 的范围改；越界不会被夹住 |
| 装了但快速压测里没有 | 插件被停用；或打开压测弹窗前插件还没加载完 | 打开启用开关；关掉弹窗重开；必要时刷新插件市场 |
| 官方卡片内容和预期不同 | 本机有同 id 的本地文件，内容优先 | 删掉/改名本地文件后刷新 |

## 7. 现有功能能否插件化

判断标准只有一条：这个功能是否只需要**声明数据**，还是需要**执行代码**。当前插件运行时没有代码执行能力，也没有插件专属的权限、进程与 API 面。

### 7.1 文档中心：可以，属于下一批最合适的扩展

现状：8 篇文档在构建时用 Vite `?raw` 打进渲染包，`KB_DOCS` 是静态数组；检索与锚点解析（`src/shared/doc-kb.ts`）是纯函数，渲染走 marked + DOMPurify。

可行性：可以新增一种数据贡献，例如：

```json
"documents": [
    {
        "title": "Acme 集群接入规范",
        "summary": "内部接入流程与命名约定",
        "markdown": "# Acme 集群接入规范\n..."
    }
]
```

需要改的地方：

1. `PluginManifestSchema` 增加 `documents` 数组（标题、摘要、正文、可选文件名），并把体积上限从「清单很小」提高到一个明确的预算；
2. `PluginContributions` 类型、`usePluginStore` 增加派生列表；
3. `DocCenter` 把插件文档与 `KB_DOCS` 合并，复用 `parseDocMeta` / `searchDocs` / `resolveAnchor`；
4. 插件市场增加「文档」分类与预览；
5. `docs/pulsar/0*.md` 仍保留为内置资源——安装包里只有 `dist`，运行时不读仓库文件。

代价与风险：文档正文会变成插件清单的一部分，8 篇内置文档合计约 92 KB，加上 JSON 转义仍能塞进当前 200,000 字符的导入上限，但更新一篇文档就要重导整份插件；没有图片/附件管线，远程图片还受生产 CSP 与 DOMPurify 限制。适合「少量、纯 Markdown、随插件版本走」的外部文档，不适合频繁编辑的 Wiki。

### 7.2 巡检：检查本身不可行，只有阈值预设勉强算数据

现状：巡检要在主进程里按集群调用 Admin REST（`src/main/services/cluster-inspection.ts`），涉及多端点采样、跨轮次比较、级别判定与报告落库。

- **检查项不能插件化**：新增一个检查 = 新增网络请求 + 判定逻辑 + 报告字段，这是代码，不是数据。要支持就得引入插件代码运行时（子进程/Worker）、API 白名单、超时与权限模型，等于重写现在的安全模型。
- **可以做数据化的部分**：按集群的阈值已经能在界面里配（`inspection_profiles`）；如果只是「一套常用阈值方案」，可以新增类似 `inspectionThresholdPresets` 的贡献，让用户一键套用。价值有限，因为阈值本来就该按集群调，且保存后是 DB 里的每集群数据，不是插件运行时数据。
- 不建议为了巡检插件化而引入任意代码执行。真要扩展检查项，优先走「内置检查 + 配置开关/阈值」的路线。

### 7.3 快速压测：预设已经插件化，引擎不行

现状：压测引擎在主进程用原生 `pulsar-client` 建 producer/consumer（`src/main/services/load-test.ts`），插件只能贡献参数。

- **参数预设**：已经支持，这是当前插件系统最主要的用途；
- **新引擎/新协议**（例如换 Kafka 协议、加自定义消息生成器、加校验逻辑）：需要代码执行与原生依赖，当前模型做不到；
- 如果只是「更多场景」，继续加 `benchmarkPresets` 即可，不需要改代码。

### 7.4 其它辅助功能

适合用「数据贡献」扩展、且不引入代码执行的候选：

| 功能 | 可贡献的数据 | 备注 |
|------|--------------|------|
| 通知消息模板 | 标题/正文模板字符串 | 需要新的渲染占位符约定；模板错误不能影响告警落库 |
| 巡检阈值方案 | 一套阈值 + 采样上限 | 套用到某个集群后仍是普通 DB 配置 |
| Topic 命名规范 | 前缀、分区数、持久化 | 已由 `topicTemplates` 覆盖 |
| 日志导出格式 | 字段顺序/表头 | 目前导出格式固定，新增前先确认需求 |

### 7.5 建议的演进顺序

1. 保持「零代码、纯数据」的一层，先把文档中心做成 `documents` 贡献（收益明确、风险最低）；
2. 需要更多表单预设时按 7.4 增加数据贡献，每一种都要有独立的 schema、上限与市场展示；
3. 只有在出现「必须执行第三方代码」的硬需求时，才引入独立进程的受限运行时，并把「可信内置扩展」与「第三方扩展」分开，绝不在主进程 `require` 插件代码。

## 8. 给插件系统加一种贡献类型（开发者清单）

如果要在本仓库里新增贡献类型，按这条链改，缺一处就会「装了没反应」：

1. `src/shared/types.ts`：定义贡献的数据结构，并挂到 `PluginContributions`；
2. `src/main/services/plugin-service.ts`：在 `PluginManifestSchema` 里加 zod 校验（范围、字符集、数量上限），并确认 `refine` 的「至少一条贡献」仍然成立；
3. `src/renderer/store/plugins.ts`：从启用条目派生新列表（停用的插件不能生效）；
4. 消费页面：把派生列表接进对应表单，明确「插件数据只预填哪些字段」；
5. `src/renderer/pages/PluginMarket.tsx`：卡片里展示新贡献的数量与内容，并按需增加筛选分类；
6. 自测：当前没有独立的插件自测脚本，至少手工覆盖「合法导入、非法 JSON、越界参数、停用后消失、卸载后消失、同 id 覆盖」六条；如果逻辑继续变多，建议新增 `scripts/plugin-selftest.cjs`，把 `parsePluginManifest` 的纯校验逻辑用 `dist` 编译产物逐条断言。

## 9. 手工验收清单

写完一个插件后按顺序走一遍：

1. `node -e "JSON.parse(require('fs').readFileSync('acme-bench.json','utf8'))"` 确认是合法 JSON；
2. 插件市场导入，看到「插件已导入并安装」且没有红色错误条；
3. 卡片显示正确的名称、版本、来源（本地）与贡献数量；
4. 打开「快速压测」，预设下拉出现「插件名 · 预设名」，套用后参数与预设一致，目标字段未被改动；
5. 新建 Topic 弹窗里模板出现；非持久模板分区数为 0；名称框为空时才填前缀；
6. 关闭插件启用开关，刷新后预设/模板消失；重新启用后恢复；
7. 卸载后文件从插件目录消失，预设/模板不再出现；
8. 故意写错一个参数（例如 `producers: 0`），导入应失败并给出字段路径，而不是「装上但没用」。
